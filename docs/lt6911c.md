# The LT6911C driver

The HDMI bridge on the RM1PE is a Lontium LT6911C on `i2c1`, address `0x2b`,
chip ID `0x516`. The published driver is Rockchip's version 00.01.00; the
device ships something newer that GL.iNet has not released. `patches/0004`
closes the gap.

Getting there took a while. Below is what is worth knowing now that it works.

## What the patch changes

**Bind to the vendor's compatible string.** The device tree says
`compatible = "lontium, lt6911"`, with a space, which is not a typo we can fix
without breaking the DTB. The published driver does not know it and never
binds.

**Enable the regulators.** The chip's supplies (`vcc1v2-lt6911`,
`vcc3v3-lt6911`) are GPIO regulators that nobody turns on. Left off, the chip
is not merely silent: it holds the whole `i2c1` bus down, and every transfer on
that bus times out.

**Wait for the chip firmware.** After reset the LT6911C loads its own firmware
from an SPI flash, which takes about 2.5 seconds. Read the chip ID before that
and it answers nothing.

**Power-cycle the rails in reset.** Toggling the reset GPIO is not enough. The
shipped driver disables both regulators, waits two seconds and re-enables them:
the analogue HDMI-RX front end needs a real power cycle to lock. The digital
side runs from the internal oscillator regardless, which is why the chip ID
reads fine while no picture ever arrives.

**Set the measurement-enable bit.** `RG_MK_PRESET_SEL` (`0xD283`) needs bit 0.
Without it `HTOTAL` reads `0xFFFF` forever, which the driver turns into
`total:131070x1460` and a frame rate of 20.

**Take the resolution GPIO as an interrupt, not a poll.** The vendor gets its
interrupt with `gpiod_to_irq()` on the `resolution` GPIO, the device tree has
no `interrupts` property, so `client->irq` is 0 and the published driver falls
back to polling once a second. That poll grabs the I2C bus 3600 times an hour,
including during the window where the chip is trying to acquire a signal.

**Kick the work once at the end of probe.** The resolution line is a pulse, not
a level. The chip usually locks about five seconds after the rails come up,
which is before the interrupt is registered, so the edge is lost and nothing
ever asks again. One `schedule_delayed_work()` at the end of probe reads the
state once. That single line is what makes a cold boot show a picture with zero
interrupts.

**Expose the sysfs attributes.** `resolution`, `real_resolution`, `version`,
`reset` and the audio ones. kvmd and `S23hdmi` both read them. See the warning
below about `version`.

**Compare timings with tolerance.** The measured pixel clock jitters by about
2 kHz, which crosses a rounding boundary between 59.99 and 60.00 fps. Compared
with zero tolerance that is a new format every second or two, and the encoder
pipeline is torn down and rebuilt each time, the picture breaks up and then
goes grey without ever reporting a signal loss. 250 kHz of tolerance, the same
value adv7604 and tc358743 use, removes it. Measurements that come back as
`0xFFFF` are dropped instead of propagated.

**Accept resolutions by rule, not by table.** The shipped driver checks that
both dimensions are divisible by four, the width is 121..4000 and the height is
121..3000. The published one compares against a list of six modes, so a
MacBook at 1920x1280, a BIOS at 1024x768 and an iDRAC at 1280x1024 are all
rejected. Note that 1366x768 fails the divisibility rule on this chip family;
that is not something we broke.

## Two things that will bite you

**1. Never ship a kernel without the `version` attribute.**
`/etc/init.d/S23hdmi` reads `/sys/bus/i2c/devices/1-002b/version` at every boot
and compares it with `49.25.3.3.1`. An empty read counts as a mismatch and runs
`lt6911c_upgrade -f v3.bin`, which erases and rewrites the chip's SPI flash and
reboots, every boot, forever. We did this once, four cycles deep, before the
serial console made it obvious. The firmware and EDID survived; the flash write
cycles did not un-happen.

If you are flashing a driver whose `version` output you have not confirmed yet,
move the script aside first. `/` is a writable overlay
(`upperdir=/userdata/overlay/upper`), so this survives a reboot:

```sh
mv /etc/init.d/S23hdmi /etc/init.d/S23hdmi.disabled
```

Put it back once the value reads correctly. It is GL's safety net for outdated
chip firmware and it also writes the EDID on first boot.

**2. Every manual register access must end with `i2c_disable`.**

```sh
i2ctransfer -f -y 1 w2@0x2b 0xff 0x80 w2@0x2b 0xee 0x00
```

Setting `0x80EE = 1` hands the bus to the host and stops the chip's internal
MCU. Leave it set and the chip cannot acquire an HDMI lock at all, permanently,
until the rails are power-cycled. A chip that is already locked survives it; one
that is still acquiring does not.

This matters more than it sounds. Poking registers to find out whether a build
locks is exactly what destroys the lock, and the result reads as "does not
work". Bracket every access, and after a cold start leave the chip alone for
30 seconds before measuring anything.

A working measurement looks like this:

```sh
i2ctransfer -f -y 1 w2@0x2b 0xff 0x80 w2@0x2b 0xee 0x01 \
                    w2@0x2b 0xff 0xa0 w2@0x2b 0x34 0x21
sleep 0.3
i2ctransfer -f -y 1 w2@0x2b 0xff 0x80 w2@0x2b 0xee 0x01 \
                    w2@0x2b 0xff 0xb8 w1@0x2b 0xb1 r3@0x2b
i2ctransfer -f -y 1 w2@0x2b 0xff 0x80 w2@0x2b 0xee 0x00      # mandatory
```
